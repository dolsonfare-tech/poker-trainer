## What This Is

CheckRaise is a Texas Hold'em skill trainer that identifies your specific weaknesses and coaches you like a human would — not a textbook. Live at **checkraise.ai** (Vercel, React).

The core moat: personalization + spaced repetition + opponent modeling + schema diagnosis. No major competitor does all four.

## Definition of Done — pass these gates before declaring ANY change complete

These apply to every model working in this repo, every session. If a change can't satisfy a gate, say so explicitly — never weaken or skip a check to get green.

1. **`npm run check:invariants`** — after EVERY code change. Mechanically enforces the "Key Decisions" and "What to Never Do" rules: single-file ownership (Supabase client/reads/writes, PostHog, AdSense, Anthropic, Sentry), no server secrets in client code, RLS + policies on every table in `schema.sql`, no tracked `.env`, no uppercase paths in `public/`, no async `onAuthStateChange` callback.
2. **`CI=true npm test`** — jest suite, after every code change.
3. **`npm run audit:scenarios`** — if `scenarios.js` or `constants.js` was touched (content consistency: pots, cards, gradings).
3b. **`npm run audit:observations`** — if `observations.js` was touched (Table Reads content gate: archetype keys, distractor discipline, replay integrity, showdown-difficulty rule, suit symbols).
4. **`npm run simulate:schemas`** — if `deriveSchema` or the rating engine was touched (exits 1 on structural diagnosis bias).
5. **New Supabase table?** It goes in `supabase/schema.sql` with RLS enabled + explicit policies (gate 1 fails otherwise), and flag to the user that the block must be run in the Supabase SQL editor BEFORE the deploy that uses it.
6. **`npm run e2e`** — after changes touching gameplay/dashboard components, App.css, or the session flow. Requires `npm run e2e:build` first (localStorage-mode build — the plain build bakes in .env's Supabase keys and boots to SignIn). Committed suite in `e2e/`: geometry guards (the July 18 table-collapse class — element sizes/overlaps, no screenshot diffing), fake-clock streak transitions, FILE line + notebook. ~30s. CI runs it on every push regardless.
7. **New load-bearing decision?** If it's an invariant (a "never do X" or "only file Y does Z"), encode it as a rule in `scripts/check-invariants.mjs` in the same session you document it — prose rules drift, exit codes don't.

## Proactive bug net (July 19, 2026 — founder-requested: proactive AND token-efficient)

Layered so the always-on layers cost ZERO LLM tokens, and model review is scoped to diffs:

1. **CI (`.github/workflows/ci.yml`)** — every push to main runs ALL gates: invariants → both content audits → jest → simulate:schemas → playtest:personas (1 trial; its mechanical invariants are the emergent-bug hunter — it caught the R4 duplicate-deal and the schema-v2 transient mislabels within hours of their creation) → production build → browser e2e. The Definition of Done stops being discipline and becomes law.
2. **Committed e2e suite (`e2e/`, `npm run e2e`)** — plain-Playwright specs against the static production build (localStorage mode, coach endpoint stubbed): GEOMETRY GUARDS (table/felt real dimensions, bubble-vs-board overlap — the class of bug where every functional test stays green while the UI is destroyed), streak transitions under a fake clock, the FILE line, the notebook no-duplication case. Deterministic element-box assertions, deliberately NOT screenshot-diffing (flaky, and diffs rot).
3. **Found-bug → permanent rule** (existing gate 7, restated): every bug class ever hit gets encoded as a mechanical check the same session — invariants rule, audit rule, jest pin, e2e guard, or harness invariant. The net only grows.
4. **Intake triage (July 19, 2026 — closes the loop from USER-reported bugs to the net).** The four user-signal channels collect on their own; this ritual is what routes them into the ratchet. Cadence: weekly at founder-only scale, and at the START of any working session once real users exist. The drill, for whoever runs it (founder or Claude):
   - **Sentry** (dashboard) — new issue types since last look. One-time founder action, still open: enable Sentry's new-issue EMAIL alerts so this channel pushes instead of waiting to be read.
   - **PostHog failure events** — `coach_read_failed` (should be zero), `profile_load_failed`, `profile_create_failed`, `scenario_disagree_failed`, `username_change_failed`, `stale_session_cleared` (a spike = sessions being revoked somewhere). Plus the comprehension heatmap: `decision_made.decision_ms` p50 + `timed_out` rate per `scenario_id` — sustained outliers are comprehension bugs (see GAMEPLAY_COMPREHENSION_FINDINGS.md C4).
   - **`scenario_feedback`** (SQL editor) — most-flagged hands: `select scenario_id, reason, count(*) from public.scenario_feedback group by 1, 2 order by count(*) desc;` — grading disputes are content bugs.
   - **`feedback`** (SQL editor) — `select category, message, created_at from public.feedback order by created_at desc limit 30;`
   Every real item becomes a work item, and the session that fixes it MUST encode the check (the ratchet law above) and stamp the relevant findings doc. A user-reported bug that gets fixed without leaving a permanent check behind is a triage failure, not a fix.
5. **LLM review policy (the token-efficiency rule):** model-driven review runs ONLY on diffs, never sweeps the codebase on a schedule. Default: Fable reviews each Opus deliverable's diff (already the working pattern — caught the em-dash prompt contradiction, the notebook duplication spec gap). For milestones (pre-launch, pre-Pro): the founder can run `/code-review ultra` (user-triggered, billed, multi-agent cloud review of the branch). Nightly/scheduled LLM sweeps are deliberately NOT part of this system — the deterministic layers above are the always-on part.

**Gameplay:**

Per-hand `scenarioId` in the `sessions.hands` payload is load-bearing (history rebuilds from it); don't remove it. **v2 upgrades (RESEARCH_LEARNING_SCIENCE.md Piece 1 R1–R3 / Piece 2 F2, zero schema change — all state derived from `sessions` rows exactly like before):** (R1) a miss is NOT one-and-done — it's on a **graduation ladder** needing *spaced* correct retrievals to clear, resurfacing on an expanding **`LADDER_SESSIONS` = [2, 5, 13]**-session interval by rung; a correct replay advances the rung, a new miss resets to rung 0. **The graduation target is GRADED (F1 fix, July 19, 2026):** a hand missed only ONCE clears on `GRADUATION_TARGET_FIRST` = **2** spaced corrects (a cheap lapse); a REPEAT offender needs `GRADUATION_TARGET_REPEAT` = **3** (the hypercorrection-relapse case). Driven by a lifetime **`misses`** count on each history entry (derived — `historyFromSessions` rebuilds it by replay, zero schema change; a legacy remediating entry with NO `misses` field is graded as a repeat = 3, the conservative default). `GRADUATION_TARGET` stays exported (= 3, the repeat/back-compat knob). **`GRADUATION_TARGET_FIRST`/`_REPEAT` are spec-fixed inside R1's 2–3-retrieval evidence range — do not widen.** (R1-surge, F1 fix) the replay slot count is **DYNAMIC**: normally 1 comeback hand/session, but SURGES to **2** while the **pool-scoped** remediation queue is deeper than `SURGE_QUEUE_THRESHOLD` = **8** (count only remediating hands whose id is in the CURRENT pool — a deep beginner queue must not surge an intermediate session). Both replays go through the same eligibility path (due rung interval + calendar-day floor + confident-miss-first ordering) and both carry `replay: true` (the honest chip); two replays still leave 3 slots (weak-skill targeting + R4 pairing untouched). Naturally re-dealt remediating hands ALREADY credit graduation (`applyHandsToHistory` keys off `remediating`, not the replay flag). (R2) the cooldown floor is **max(N sessions, 1 calendar day)** — chained same-day sessions ("Deal Next Session →") can't resurface a same-day miss (session-count-only cooldowns are massed practice in disguise). Wall clock: `sessions.created_at` (Supabase, now in the fetch select) / `toLocalDateString(new Date())` (local); passed as `buildSession({ currentDate })` and `applyHandsToHistory(..., sessionDate)`. (F2) each hand's **`decisionMs`** is captured additively in the `hands` payload — fast+wrong (`≤ CONFIDENT_MISS_MS` = 15s) ≈ a high-confidence error: those `lastMissConfident` misses jump the resurface queue and the flag rides the replay object + coach-read payload (`confidentMiss`). History entries now carry `{ …, lastSeenDate, remediating, rung, lastMissConfident }`; the ladder math lives in `applyHandsToHistory` (pre-v2 entries degrade gracefully via `remediating ?? lastResult==='incorrect'`). Do NOT add per-item SM-2/FSRS ease — R3: a fixed ladder is within noise at this pool size and far more debuggable. **(R4, July 18, 2026) Contrast-pair-aware dealing:** when a weak-skill slot seats a scenario that belongs to an authored `CONTRAST_PAIRS` group (`scenarios.js`) with an eligible same-pool partner, the builder also seats that partner (a general slot) and lays them ADJACENT in the dealt order — the juxtaposition is the interleaving that makes the contrast teach. Capped at `MAX_CONTRAST_PAIRS_PER_SESSION = 1`; never touches the replay slot; respects the per-skill + preflop caps. ## What to Never Do

- Never hardcode the Claude API key — use the `CLAUDE_API_KEY` env variable (server-side only, set in Vercel)
- Never call the Claude API from any file except `api/coach-read.js` — client code goes through `src/utils/claude.js`
- Never expose the API key to the browser (no `REACT_APP_`-prefixed key variables)
- Never add `tag` or `villain.label` fields back to scenario objects — they're derived at runtime
- Never use shorthand card notation (KQs, 98d) — always use suit symbols
- Never add Tailwind to existing Phase 1 CSS — only on new screens if adopted
- Never modify `scenarios.js` for UI work — it's content, not layout
- Never commit `.env` to GitHub
- Never add answer-until-correct / re-attempt to the SCORED main loop — it corrupts the skill-accuracy ratings the whole rating engine stands on (RESEARCH_LEARNING_SCIENCE.md F4). An unscored "replay this hand" study mode is the acceptable form.
- When authoring scenario feedback text: the fb must explain WHY (price, position, villain type) — never just restate or dress up the action taken. Explanation quality is the highest-effect-size lever in the product (F1).
- Never `await` Supabase (or any async) calls inside the `onAuthStateChange` callback — supabase-js holds its auth lock during the callback and authed calls need that lock, so it deadlocks intermittently (the "stuck on Shuffling up…" bug, July 2026). Defer with `setTimeout(async () => {...}, 0)`.
